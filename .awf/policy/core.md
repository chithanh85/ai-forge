# AWF Core Policy

This file is the canonical, client-neutral operating policy for AI agents working in an AWF-managed repository. Client files such as `AGENTS.md`, `GEMINI.md`, and `CLAUDE.md` are adapters. When they conflict with this file, this file wins unless a project-local user rule explicitly overrides it.

## 1. Preflight

- Read `.planning/STATE.md` and `.planning/PROJECT.md` when present.
- Read `docs/wiki-index.md` when present and use relevant project knowledge before implementation.
- For non-trivial work, recall relevant Second Brain knowledge when the integration is available; otherwise use the local fallback under `.agent/skills/auto-memory/` when present.
- Inspect Git branch, HEAD, and working tree before modifying code. Do not overwrite unrelated user changes.
- Prefer repository evidence over chat assumptions.

## 2. Work intake and risk lane

Classify work before implementation. Use `docs/FEATURE_INTAKE.md` when present.

- Tiny: no meaningful blast radius; compact plan is acceptable.
- Normal: explicit plan then implementation.
- High risk: plan, design, implementation, audit, and explicit approval when the risk gate requires it.

For non-trivial work define expected output, acceptance criteria, scope boundary, non-negotiable constraints, and touchpoints before implementation.

## 3. Simplicity and bounded change

Use the first viable rung:

1. Does this need to exist?
2. Does the codebase already solve it?
3. Can the standard library solve it?
4. Can a native platform feature solve it?
5. Can an already-installed dependency solve it?
6. Can the solution be materially simpler?
7. Only then add new code or dependencies.

Touch only what the task requires. Do not opportunistically rewrite unrelated code. Preserve established project style unless the task explicitly changes it.

## 4. Verification-driven execution

- Treat every implementation claim as a hypothesis until verified.
- Bug fixes require a regression test whenever practical.
- Prefer Red → Green → Refactor for behavioral changes.
- Do not report DONE based only on worker/agent claims; verify artifacts, tests, Git state, and expected behavior.
- A placeholder command such as `echo "Configure build"` is `NOT_CONFIGURED`, not proof of a successful production build.

Logical quality commands live in `.awf/manifest.json` under `toolchain.commands`. Do not hard-code `npm`, `pnpm`, `yarn`, or `bun` when a manifest command is available.

## 5. Contract and artifact gate

For non-trivial plan/code/debug work, use a run directory under `.agent/artifacts/<run-id>/` containing:

- `context-snippets.json`
- `risk-gate.json`
- `verification.json`
- `review-decision.json`
- `adversarial-validation.json`

Completion is blocked by missing/invalid evidence, blocking risk/review decisions, failed verification commands, or failed adversarial validation. Runtime artifacts belong to the current project/session; template development history must not be treated as project history.

## 6. Rationalization prevention

Before code or completion claims, consult `.agent/rules/rationalization-prevention.md` when present. Do not waive tests, security checks, or evidence merely because a change is small, urgent, generated by AI, or appears obvious.

## 7. Security

- Never commit secrets, tokens, real `.env` files, private keys, or credentials.
- Treat external installer scripts and executable package fetches as supply-chain boundaries. Pin executable integration versions; avoid runtime `@latest` in managed configuration.
- Do not bypass client sandbox/approval/trust protections from a shared AWF workflow. Elevated permissions are an explicit operator decision, not a framework default.
- Apply Red Team review before deploy or high-risk merge.

## 8. Database defaults

When a task introduces or changes persistent relational data, default to UUID/ULID identifiers, timezone-aware timestamps, indexed foreign keys, and N+1 prevention unless the project architecture explicitly requires otherwise. Do not force database conventions onto projects where they are irrelevant.

## 9. Optional capabilities and integrations

AWF core must work when optional integrations are unavailable. Detect capabilities instead of assuming them.

Examples include GitNexus, Second Brain, Teleport, Open Design, Clawpatch, browser automation, and external AI providers. Use an available integration only when it materially improves the task. Never assume a repository index name, sibling-directory layout, provider, or model identifier from template history.

## 10. Model and agent routing

AWF specifies roles/capabilities, not vendor model names. Examples:

- planner: high-reasoning capability
- implementer: coding capability
- reviewer: independent-review capability

The active client, router, or user configuration resolves those capabilities to actual models. Do not pin a model in core workflows unless a project explicitly opts into that model.

When work has independent subtasks and the active client supports safe parallel agents, parallelize bounded independent work. Otherwise execute sequentially. Parallelism is an optimization, not a correctness requirement.

## 11. File hygiene and runtime state

- Project docs belong in `docs/`; scripts belong in an appropriate `scripts/` area.
- Temporary work belongs under `.tmp/` or another ignored runtime directory.
- Runtime artifacts/checkpoints must not leak template-maintainer session state into projects created from the template.
- Preserve user-authored content outside AWF managed regions.

## 12. Context and handoff

As context becomes constrained, stop broad exploration, save an evidence-backed checkpoint, and narrow work to verified next actions. Never use context pressure as a reason to skip verification.

At handoff report:

- WHAT changed
- WHY it changed
- EVIDENCE produced
- VERIFICATION run and result
- GIT state
- NEXT action or remaining risk

Save durable lessons after meaningful bug fixes or architecture decisions when Second Brain is available.
